# 提案：世界组（World Groups）

- 状态：**已讨论、暂缓实施**（2026-11-17 决定晚点再做）
- 类型：组织 / 目录结构重构
- 关联提案：[构建期清单生成](build-time-manifest.md)（互补方案）

## 1. 背景与动机

当前多个 agent 并行向仓库新增世界。所有世界共用一份 `worlds/manifest.json`，且根 `index.html` 内有一份内联兜底副本（`file://` 双击可用）。每次新增世界都要改这两个**共享文件**，两条分支各自追加条目时必然产生合并冲突（现状：保留双方条目后重跑 `tools/sync-manifest.mjs` 即可，成本尚低）。

世界组的目标是用**所有权切分**把共享写降到最低：每个 agent 只在自己的组内加世界，总目录只加载「组」，不直接加载世界。

## 2. 方案概述

- 引入「世界组」层级：一个组 = 一个 agent（或一个主题）的世界集合，拥有自己的组大厅页与组内清单。
- 总大厅（根 `index.html`）只渲染组卡片，点击进入组大厅；组大厅再渲染组内世界卡片。
- 新增世界 = 只在自己组目录内新增文件 + 改自己组的清单 → 跨 agent 改动互不相交，合并干净。
- 新建组 = 才需要写共享的「组注册表」→ 冲突频率从「每加一个世界」降到「每建一个组」。

## 3. 目录布局

```
├── index.html                  # 总大厅：只加载组注册表
├── groups/
│   ├── manifest.json           # 组注册表（共享，仅建组时写）
│   └── <group>/
│       ├── index.html          # 组大厅：加载本组清单（含内联兜底）
│       ├── manifest.json       # 本组世界清单（单写者：本组 agent）
│       └── worlds/
│           └── <slug>/
│               ├── index.html  # 世界本体（单文件自包含）
│               ├── preview.jpg
│               └── README.md
└── tools/sync-manifest.mjs     # 升级为双层同步
```

### 3.1 back 链接约定保持不变

现有 AGENTS.md 要求世界页右上角 `<a class="back" href="../../index.html">`。在上述布局下该约定在两级都天然成立：

- 世界页 `groups/<g>/worlds/<slug>/index.html` → `../../index.html` = `groups/<g>/index.html`（组大厅）。
- 组大厅 `groups/<g>/index.html` → `../../index.html` = 根 `index.html`（总大厅）。

因此**不需要修改 back 规则**，只需迁移目录与清单路径。

### 3.2 清单字段

- 组注册表 `groups/manifest.json`：沿用现有字段 schema，但 `entry` 指向组大厅 `groups/<g>/index.html`，`cover` 指向组封面；可加 `owner` 字段标明负责 agent。
- 组内 `groups/<g>/manifest.json`：与现有 `worlds/manifest.json` 完全同 schema（id/name/nameEn/description/entry/cover/tags/added），`entry`/`cover` 为相对根的路径 `groups/<g>/worlds/<slug>/…`。

### 3.3 file:// 离线

两级大厅各自内联一份兜底副本（总大厅内联组注册表；组大厅内联本组清单）。`http(s)` 下 fetch 对应 JSON、失败回退内联；`file://` 下直接读内联。离线双击在两级都可用。

## 4. 冲突分析（诚实结论）

**能大幅降低，但不是绝对零冲突。**

- 消除的部分：世界本体文件、组内清单均为单写者（一人一组），跨 agent 新增世界互不相交 → 无冲突。
- 残留的部分：
  1. 共享的组注册表 `groups/manifest.json` + 根内联副本，仅在**新建组**时被写。两个 agent 同时建组仍会冲突（低频；解决方式同现状：保留双方 + 重跑 sync）。
  2. 若两个 agent **共用一个组**，组内清单回到多写者，冲突回归。故「一人一组」是前提。
- 结论：冲突概率从「每次加世界」降为「每次建组」，并未归零。

## 5. 配套改动

- `tools/sync-manifest.mjs` 升级为双层：同步根组注册表 → 根内联；遍历各组同步组清单 → 组内联；`--check` 校验两级一致与路径/封面体积。
- AGENTS.md 重写：目录树、新增世界步骤（改为「在所属组内新增」）、清单 schema 拆两级、sync 步骤、组注册表维护规则。
- 迁移现有 7 个世界进一个默认组（如 `groups/collection/`），更新 entry/cover 路径、根大厅改为组列表、各组封面。
- 大厅 UI：组卡片层 + 组内世界卡片层（复用现有卡片样式）。

## 6. 成本

- 导航多一层（总大厅 → 组 → 世界）。
- 页面与内联副本数量增加（每组一份），维护面变大。
- 「唯一数据源」变成分布式多处（根组表 + 各组清单），靠单写者纪律维持一致。
- 一次性迁移 churn：移动全部现有世界、改路径、重写 AGENTS。
- 跨组搜索 / 标签聚合需要额外设计（总大厅不再直接持有世界列表）。

## 7. 与「构建期生成」的关系

- 世界组 = **靠所有权切分**减少共享写（组织层方案，不需要 CI）。
- 构建期生成 = **靠单一写者（CI bot）**彻底去掉人手共享写（技术方案，不加导航层），见 [build-time-manifest.md](build-time-manifest.md)。
- 两者互补：组解决「谁负责哪块」，生成解决「共享文件谁来写」。只上组仍留建组时的小冲突；只上生成则零人手共享写但无组织层。可叠加。

## 8. 建议与触发条件

- 现状冲突成本极低（一份 manifest + 内联块，保留双方重跑 sync），**迁移到组的收益暂时不大**，故暂缓。
- 若想现在就根治冲突，优先做构建期生成（不动导航）。
- 当 agent / 世界数量明显增多、需要按 agent 或主题策展时，再切世界组；届时可与构建期生成叠加。
- 开放问题：组命名与 ownership 规则；现有世界是迁移还是保留为 legacy 平铺组；组封面来源；跨组搜索 / 标签；总大厅是否保留「最近新增」跨组聚合。
