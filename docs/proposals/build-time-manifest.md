# 提案：构建期清单生成（Build-time Manifest）

- 状态：**已讨论、暂缓实施**（2026-11-17）
- 类型：工具 / CI 流程
- 关联提案：[世界组](world-groups.md)（互补方案）

## 1. 背景与动机

同 [world-groups.md](world-groups.md) 第 1 节：共享的 `worlds/manifest.json` + 根内联副本是多写者文件，每次新增世界都可能合并冲突。本提案用**单一写者**根治：清单不再由人手编辑，而由机器在合并后的单一串行点生成。

## 2. 关键澄清：为什么「提交前本地跑一次」不行

一个直觉方案是「每个贡献者提交前本地重新生成清单」。这**不能**消除冲突：两条分支各自生成并提交同一个派生共享文件，合并时照样撞。自动生成只是把手改换成机器改，没有改变「双方都写同一个文件」这一根源。

正确做法是把生成移到**合并之后、main 上的单一串行点**，贡献者分支完全不碰共享文件。

## 3. 方案概述

- 每个世界只在自己目录放一份元数据 `worlds/<slug>/world.json`（name / nameEn / description / tags / added）。新增世界 = 只新增文件，跨分支互不相交。
- `worlds/manifest.json` 与根内联副本标记为**生成物**，人不手改。
- 零依赖脚本 `tools/build-manifest.mjs` 扫描 `worlds/*/world.json`，生成 manifest 并注入根内联（现 `sync-manifest.mjs` 的升级版）。
- GitHub Actions 在 push / merge 到 main 时运行该脚本，作为一个 **bot 提交**回 main。bot 在 main 上串行运行、每次基于合并后的完整目录生成 → 不存在「两条分支各写一份」的分叉。
- 在途分支不受 bot 提交影响：它们没改 manifest，合并时 git 直接采用 main 侧版本，不冲突；合并完 bot 再补登记。即使两个 PR 几乎同时合并，bot 也排队各跑一次，最终状态正确。

## 4. 离线约束如何保持

bot 把生成结果**提交回 main**，因此 main 上始终有一份已提交的、最新的内联清单；双击 / 下载 zip 离线可用。这是相对「部署期生成」变体的关键优势。

## 5. 前提与代价

- main 需允许 bot 直接 push（若开分支保护需给 bot 放行或改走 PR）。
- 清单成为生成物：人手改 manifest 会被下次 bot 覆盖；贡献者改元数据请改 `world.json`。
- 需要一个 Actions 工作流与 `GITHUB_TOKEN contents:write`。
- 本地仍可跑 `build-manifest.mjs --check` 做提交前校验（只校验、不写共享文件）。

## 6. 不推荐的变体：部署期生成

清单完全不进 git、只在 Actions 部署时生成进 Pages 产物 → 冲突彻底为零，但 repo 双击离线就没有清单，违背「单文件离线、file:// 可开」的核心约定。故不推荐。

## 7. 与世界组的关系

- 本提案 = 技术层单一写者，**不加导航层**，零人手共享写。
- 世界组 = 组织层所有权切分，仍留「建组时」的小冲突。
- 互补可叠加：组负责策展 / ownership，生成负责共享文件单写。

## 8. 建议与触发条件

- 若想在不动导航的前提下现在就根治冲突，优先做本提案。
- 现状冲突成本极低，亦可继续维持手动登记 + sync，等规模上来再做。
- 开放问题：bot 提交是否触发分支保护 / CI 循环；`world.json` 与现有 manifest 字段的一次性迁移；是否保留 `sync-manifest.mjs` 作为兼容入口。
